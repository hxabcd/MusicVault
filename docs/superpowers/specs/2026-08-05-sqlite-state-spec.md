# SQLite 状态存储 Spec

状态：已完成（2026-08-12）
范围：本次工程重构

## Problem Statement

当前曲目、歌单、同步索引和处理索引分散在多个 JSON 文件中。多个流程需要同时修改这些文件，容易出现部分写入、重复迁移、状态不一致和重复的解析逻辑。

随着 preset、media_store 和目标同步能力增加，JSON 文件无法清晰表达曲目、歌单、媒体资产和目标关系，也无法支持可靠事务。

## Solution

使用单个 SQLite 数据库作为本地状态唯一来源。数据库负责保存结构化业务状态，文件系统只保存媒体资产、缓存文件和导出视图。

通过 Repository 封装 SQL，通过版本化 schema migration 管理数据库演进。所有跨实体更新在一个事务中完成。

初始领域数据包括：

- tracks：标准化曲目和源元数据；
- playlists：歌单信息；
- playlist_tracks：曲目与歌单关系；
- managed_songs：单独管理的曲目；
- media_assets：media_store 中的媒体资产、规格、路径和摘要；
- preset_registry：已加载 preset 的名称、来源、API 版本和启用状态；
- export_targets：目标标识和目标类型。

同步历史和每个 preset 的运行历史属于后续 spec，不在本次落地。

## User Stories

1. 作为用户，我希望一次同步中的相关状态能够原子更新，以免中断后产生半完成状态。
2. 作为项目维护者，我希望通过关系表表达歌单和曲目关系，以便处理多歌单共享曲目。
3. 作为项目维护者，我希望媒体资产有明确的数据库记录，以便不依赖文件名猜测 track_id。
4. 作为项目维护者，我希望数据库可以通过 schema migration 演进，而不依赖手工修改 JSON。
5. 作为用户，我希望数据库损坏时可以通过 media_store 和 library 重建基础索引。
6. 作为项目维护者，我希望 Repository 可以在测试中替换为临时数据库。
7. 作为 preset 作者，我希望读取曲目、歌单和媒体资产时使用稳定查询接口。
8. 作为项目维护者，我希望删除歌单时可以在一个事务中更新关系、索引和管理记录。
9. 作为用户，我希望状态文件不再需要多个 JSON 文件之间的手工同步。
10. 作为项目维护者，我希望数据库结构明确区分源数据、媒体资产和目标导出状态。
11. 作为开发者，我希望迁移失败时程序停止并保留原数据库，避免静默损坏。
12. 作为用户，我希望重建索引不会覆盖无法识别的媒体文件。

## Implementation Decisions

- 使用 SQLite 和 Python 标准库 `sqlite3`，暂不引入 ORM。
- 使用明确的 Repository 接口隔离 SQL。
- 使用 schema version 表和顺序迁移脚本。
- 所有写操作默认在 application 用例控制的事务中执行。
- JSON 不再作为运行时状态主存储。
- 不保留旧 JSON 的完整读写兼容层；需要迁移时提供一次性导入或重建能力。
- 数据库不保存媒体二进制内容，只保存媒体资产元数据和路径。
- 目标端的 manifest 和同步历史属于后续扩展。
- 任何无法确定归属的文件不得被自动删除。

## Testing Decisions

- Repository 测试使用每个测试独立的临时 SQLite 数据库。
- 测试事务提交、回滚、重复插入、唯一约束和迁移顺序。
- application 测试验证多个 Repository 更新是否具有原子性。
- 重建索引测试只验证可识别文件被导入，不验证内部 SQL 写法。
- 迁移测试从每个支持的旧 schema 版本升级到最新版本。
- 参考现有配置模型和同步状态测试，保留数据 round-trip 思路，但改为数据库行为测试。

## Out of Scope

- PostgreSQL、MySQL 或远程数据库。
- ORM 和通用数据库抽象框架。
- 每个 preset 的同步历史。
- 目标端 manifest 的持久化。
- 数据库多用户并发访问。

## Further Notes

SQLite 是本地单进程状态库。媒体文件和导出目录不是数据库的替代品，而是由数据库描述和管理的外部资源。
