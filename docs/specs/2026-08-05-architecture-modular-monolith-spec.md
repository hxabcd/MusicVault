# 模块化单体与端口适配器架构 Spec

状态：规划中
范围：本次工程重构

## Problem Statement

当前项目已经形成 CLI、Service、Adapter、Core 的雏形，但职责边界仍不稳定。同步服务、处理服务和运行服务同时承担业务编排、文件系统操作、状态持久化、外部 SDK 调用和终端输出。

这种结构使一个局部变化容易影响整条流水线，也使测试必须依赖大量具体实现。未来 preset 将由 Python 脚本定义，并可能连接本机目录、其他设备或播放器，因此需要稳定的扩展边界。

## Solution

将项目重构为模块化单体，并采用端口适配器思想。项目仍以单进程、本地文件系统和 SQLite 为主要运行方式，不拆分微服务。

依赖方向固定为：

```text
presentation → application → domain
adapters ───────────────────┘
```

核心分层职责如下：

- `domain`：曲目、歌单、媒体资产、preset 定义、同步规则和值对象；不得依赖 CLI、Rich、SQLite、网易云 SDK 或 ffmpeg。
- `application`：同步、处理、导出、重建索引等用例；负责流程编排和事务边界。
- `ports`：API、状态仓储、媒体处理、目标同步、文件操作等抽象接口。
- `adapters`：网易云 SDK、SQLite、文件系统、ffmpeg、mutagen、外部设备和播放器 API 的具体实现。
- `presentation`：CLI 参数解析、交互式登录、终端输出和退出码。

所有具体依赖在 composition root 中组装；业务用例不自行创建数据库连接、SDK 客户端或 Rich 控制台。

## User Stories

1. 作为项目维护者，我希望核心业务规则不依赖外部 SDK，以便替换网易云 SDK 时不必重写同步逻辑。
2. 作为项目维护者，我希望文件系统副作用通过端口访问，以便使用临时目录或 fake 实现测试同步流程。
3. 作为项目维护者，我希望 CLI 只负责输入和展示，以便未来增加非交互命令或其他入口。
4. 作为 preset 作者，我希望只依赖公开 API，而不是内部 Service，以便内部重构不会频繁破坏 preset 脚本。
5. 作为用户，我希望下载、处理、同步和导出仍在一个本地程序中完成，以便不增加部署和运维成本。
6. 作为测试作者，我希望可以在不访问网易云和不运行 ffmpeg 的情况下测试主要用例。
7. 作为项目维护者，我希望每个模块有单一主要变化原因，以便定位变更影响范围。
8. 作为项目维护者，我希望基础设施异常能转换为稳定的应用错误，以便 CLI 可以正确返回失败状态。
9. 作为项目维护者，我希望 composition root 集中创建具体实现，以便不同运行模式可以装配不同适配器。
10. 作为用户，我希望保留当前 CLI 工具形态，同时允许内部架构进行破坏性重构。

## Implementation Decisions

- 采用模块化单体，不引入微服务、消息队列或远程服务拆分。
- 将同步、处理、媒体生成和目标同步建模为应用用例。
- 将状态仓储、媒体仓储、目标端操作、下载、解密、转码和元数据写入定义为端口。
- 端口只描述业务需要的能力，不暴露具体第三方类型。
- preset 脚本只能依赖版本化公开 preset API。
- 不为每个小函数创建接口；只在外部依赖、高副作用或未来变化明显的边界建立端口。
- Rich 输出和 CLI 退出码由 presentation 层决定，application 层返回结构化结果。
- 允许破坏现有内部目录和状态结构，但本次不引入远程目标和双向同步功能。

## Testing Decisions

- 最高测试接缝是 application 用例，使用 fake ports 验证外部行为。
- domain 测试只验证规则、值对象和状态转换，不验证实现细节。
- adapter 测试使用临时 SQLite、临时文件系统和 mock 外部 SDK。
- preset 脚本测试通过公开 API 加载并执行，不直接测试内部模块。
- 现有曲目模型、歌词解析和 preset 模型测试作为既有测试基础继续保留。
- 每个应用用例至少覆盖成功、部分失败、依赖失败和取消场景。

## Out of Scope

- 微服务化。
- 双向同步。
- 外部播放器的具体实现。
- 同步历史和保留策略的实现。
- 为所有现有函数机械创建接口。

## Further Notes

本架构允许未来增加目标同步器、设备适配器和播放器 API，而不改变 domain 与主要 application 用例。
